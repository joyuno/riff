# MVP Bench 비개발 창업자 벤치마크 설계

**작성일:** 2026-08-05
**상태:** 사용자 검토 대기

## 한 문장

> Can a non-developer turn one brief into a researched, proven MVP?

`MVP Bench`는 같은 Codex 모델과 검색 권한에서 Riff, GSD, gstack이 비개발
창업자를 아이디어 한 문장에서 조사 근거가 있고 실제로 작동하는 MVP까지 얼마나 잘
안내하는지 비교하는 공개 파일럿 벤치마크다.

공개 캠페인 문구는 **From one brief to a researched, proven MVP.**로 한다.

## 목표

- 비개발 창업자가 기술적 개입 없이 MVP를 완성할 수 있는지 측정한다.
- 초반 자료조사가 검증 가능한 근거와 제품 결정으로 이어지는지 측정한다.
- 에이전트의 완료 선언이 아니라 숨겨진 acceptance test로 결과를 판정한다.
- 성공 화면뿐 아니라 실패, 마찰, 비용과 원자료를 함께 공개한다.
- Riff에 유리하도록 결과를 조정하지 않고 재현 가능한 비교 프로토콜을 남긴다.

## 비목표

- 모델 자체의 성능 비교
- 배포, 실제 결제, 외부 AI·SaaS API 품질 평가
- 팀 협업과 장기 유지보수 평가
- 9회 결과만으로 통계적 우월성 또는 보편적 최강을 주장하는 것

## 파일럿 범위

| 항목 | 고정값 |
|---|---|
| 참가자 | 비개발 창업자 1명 |
| 비교 대상 | Riff, GSD, gstack |
| 실행 횟수 | 도구당 3회, 총 9회 |
| 호스트 | Codex |
| 모델·reasoning | 모든 실행에서 동일, 실행 메타데이터에 기록 |
| 검색 | 동일한 Codex 네이티브 웹 검색, 별도 가입·API 키 없음 |
| 시간 | 제한 없음, 완료까지의 시간을 효율 지표로 기록 |
| 시작 상태 | 동일한 React/Vite starter의 새 저장소 |
| 정상 종료 | 검증된 MVP 완료 |
| 실패 종료 | 사용자 포기 또는 동일 blocker 3회 반복 후 미해결 |
| 직접 코딩 | 참가자 코드 수정 금지 |

## 과제

### A. 예약·노쇼 관리 SaaS

첫 요청:

> 1인 미용실 사장님이 예약을 관리하고 노쇼를 줄일 수 있는 웹앱을 만들어줘.

핵심 행동은 예약 등록, 시간 충돌 방지, 예정·완료·취소·노쇼 상태, 오늘 일정과
예상 매출, 필터, 로컬 저장, 모바일 사용성이다.

### B. 고객 리뷰 인사이트 도구

첫 요청:

> 온라인 쇼핑몰 리뷰를 한눈에 보고 개선할 점을 찾는 웹앱을 만들어줘.

핵심 행동은 fixture 리뷰 불러오기, 긍정·부정 및 주제 분류, 개선 우선순위, 처리
상태, 필터, 요약 통계다. 외부 AI 호출은 사용하지 않는다.

### C. 견적·고객 진행 관리 SaaS

첫 요청:

> 프리랜서가 견적서를 만들고 고객 진행 상태를 관리하는 앱을 만들어줘.

핵심 행동은 고객과 견적 항목 등록, 수량·단가·부가세·총액 계산,
초안·발송·승인·거절 상태, 검색·필터, 요약 매출, 로컬 저장, 인쇄 화면이다.

세 과제는 입력, 상태 전환, 계산, 필터, 검증, 저장과 완성된 UI를 공통으로 요구한다.

## 초심자 응답 규칙

각 과제에는 모델이 볼 수 없는 사용자 답변 카드를 둔다. 참가자는 질문받은 항목만
카드대로 답하고 조건을 먼저 제공하지 않는다.

- 기술 질문: `잘 모르겠어요. 초심자에게 가장 단순한 방법으로 추천해서 진행해주세요.`
- 추천이 있는 선택: 추천안 선택
- 추천이 없는 선택: 첫 번째 선택
- 요청하지 않은 기능: 추가하지 않음
- 오류: 보이는 현상만 전달하고 원인을 추측하지 않음
- 구현 명령, 코드, 테스트 힌트: 먼저 제공하지 않음

질문 수는 제한하지 않는다. 핵심 질문, 불필요한 기술 질문, 위험한 무질문 추측을
각각 기록한다.

## 자료조사

세 도구는 같은 Codex 네이티브 웹 검색을 사용할 수 있다. Exa 또는 별도 검색
플러그인 설치, 회원가입, API 키 입력은 요구하지 않는다. 조사 시간과 검색 횟수는
제한하지 않으며 결과의 충분성과 효율을 함께 기록한다.

각 실행은 구현 전에 `RESEARCH.md`를 남긴다.

```text
조사 질문
출처와 확인 날짜
근거가 뒷받침하는 사실
아직 불확실한 가정
조사로 결정하거나 바꾼 MVP 범위
```

출처 개수 자체는 점수가 아니다. 최신성이 필요한 주장에는 최신 출처를 사용하고,
가능하면 공식·1차 출처를 우선한다. 검색 결과를 나열하기만 하고 제품 결정에 연결하지
못하면 조사 완료로 인정하지 않는다.

## 실행 절차

1. runner가 동일 starter에서 익명 실행 저장소를 생성한다.
2. 지정된 비교 도구 하나만 활성화하고 새 Codex thread를 연다.
3. 공개 첫 요청을 그대로 입력하고 시간·turn·비용 기록을 시작한다.
4. 참가자는 답변 카드와 초심자 응답 규칙만 사용한다.
5. 에이전트의 완료 선언 후 grader를 실행하고 critical 실패가 있으면 현상만 전달한다.
6. 성공 조건 충족, 사용자 포기 또는 동일 blocker 3회 반복 시 실행을 종료한다.
7. 저장소와 메타데이터를 봉인하고 도구 이름을 제거한 익명 ID로 최종 grader를 실행한다.
8. 참가자가 난이도와 만족도 설문을 작성한다.
9. 9회가 끝난 뒤 테스트, transcript, 화면, 실패와 결과표를 공개한다.

grader와 답변 카드는 실행 저장소 밖에 두며 실행 중인 에이전트에 노출하지 않는다.

## 지표

### 1차 지표

- **MVP 완성률:** 성공 실행 수 / 3
- **Acceptance 통과율:** 숨겨진 기능 테스트 통과 비율
- **초심자 기술 개입:** 참가자가 명령, 코드 또는 원인 분석을 제공한 횟수
- **근거-결정 연결률:** 조사 근거가 실제 제품 결정으로 추적되는 비율

### 2차 지표

- 첫 실행 화면과 최종 완료까지의 시간
- 조사 시간, 검색 횟수와 사용 출처
- 질문 및 사용자 응답 수
- 핵심 질문 누락과 불필요한 기술 질문 수
- 오류 반복 및 복구 횟수
- 완료 선언 후 발견된 실패 수
- turn, 토큰, 비용
- 참가자 난이도와 만족도 1~5점

임의 가중치의 단일 종합점수는 만들지 않고 중앙값과 원자료를 공개한다.

## 성공 판정

한 실행은 다음 조건을 모두 만족해야 성공이다.

- 필수 acceptance test 90% 이상
- critical 기능 실패 없음
- 로컬 앱이 실제 실행됨
- 새로고침 후 핵심 데이터 유지
- 조사 근거와 핵심 제품 결정이 연결됨
- 참가자가 코드를 직접 수정하지 않음

시간은 성공 조건이 아니다. 같은 blocker가 세 번 반복되고도 해결되지 않거나 사용자가
비용·시간 때문에 중단하면 실패로 기록한다.

과제별 grader는 동일 점수 구조를 사용한다.

| 영역 | 점수 |
|---|---:|
| 입력 생성 | 15 |
| 목록 표시 | 10 |
| 상태 변경 | 15 |
| 삭제 | 10 |
| 필터 | 10 |
| 계산·집계 | 15 |
| 입력 검증 | 10 |
| 새로고침 영속성 | 15 |

## 공개 산출물

```text
benchmarks/mvp-bench/
```

실험 전에 protocol, task, 답변 카드 해시, grader 판정 기준을 커밋한다. 결과 발표 시
플러그인·Codex 버전, 모델, prompt, 응답, 시간·비용, 저장소, 테스트 결과, 주요 화면과
실패를 공개한다. 민감정보는 제거한다.

## README 표현

첫 화면은 결과표보다 질문과 실제 결과물을 먼저 보여준다.

```text
MVP Bench
Can a non-developer turn one brief into a researched, working MVP?

Same Codex model. Same startup briefs. Same web access.
No manual code edits. No artificial time limit. Hidden acceptance tests.
```

이후 세 제품의 실제 화면, 완료 선언 대비 테스트 통과, 초심자 마찰, 실패 사례,
도구별 원자료 순서로 배치한다.

허용되는 결론:

> In this nine-run pilot, Riff helped one non-developer founder ship more
> researched, acceptance-complete MVPs with fewer technical interventions.

실제 결과가 이를 지지할 때만 사용한다. `Riff가 세계 최고의 하네스` 같은 보편적
우월성 주장은 하지 않는다.

## 공개 한계

README와 결과 문서에 다음을 눈에 띄게 표시한다.

- Pilot study
- One non-developer founder
- Three startup briefs
- Three runs per harness, nine total
- Maintainer-run, not an independent study
- Same Codex model; 다른 모델과 호스트에는 일반화하지 않음

## 완료 조건

- 9개 새 저장소를 만들고 익명 run ID를 부여할 수 있다.
- 세 과제의 hidden grader가 starter의 의도된 성공·실패 fixture를 구분한다.
- 실행 메타데이터와 사용자 설문을 같은 스키마로 저장한다.
- 도구 이름을 보지 않고 grader 전체를 실행할 수 있다.
- 결과를 재계산하는 단일 명령이 존재한다.
- README에 원자료와 재현 절차를 연결할 수 있다.
