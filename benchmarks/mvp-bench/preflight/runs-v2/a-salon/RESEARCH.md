# RESEARCH — 조사 근거와 제품 결정

Exa 웹 검색 3건(예산: core-closure 중 결정을 바꿀 가능성이 가장 큰 질문 3개). 미용실 사용자 문제·예약 관행·경쟁 제품 조사로 범위를 한정했다.

## 검색 1 — 미용실 노쇼 방지 관행

- 질의: "1인 미용실 예약 노쇼 방지 예약금 리마인드 문자 관행"
- 출처: [미용실과 스파에서 예약 불이행 및 막판 취소를 줄이는 방법](https://get.mytime.com/ko/resource-center/blog/how-to-reduce-no-shows-and-last-minute-cancellations-in-salons-and-spas/) (제품 도움말, industry) / [예약 부도 '노쇼' 때문에 울상 짓는 미용업계](https://www.asiae.co.kr/article/2025010916193771688) (기사, KR/2025-01-09)
- 확인한 것:
  - 예약 1~2일 전 리마인더가 노쇼율을 크게 낮추는 표준 관행이다(자동 문자 발송 전제).
  - 예약금·위약금 제도는 국내에서 법적 강제성이 없고(공정위 권고 기준일 뿐) 미용업계 전용 기준도 없어 분쟁 소지가 크다.
- 제품 결정에 미친 영향:
  - 리마인더는 자동 문자 발송(외부 SMS 연동) 없이도 가치가 있는 부분(내일 예약 목록을 보여줘서 사장님이 직접 연락)만 재질문으로 확인 → 창업자가 "필요"로 확정. **결정: '내일 예약 보기' 화면 추가, 자동 발송은 이번 범위 밖.**
  - 예약금·위약금은 법적 근거도 약하고 창업자가 이미 "카드 결제는 카드단말기로"라고 결제 기능을 원치 않았으므로 조사만 하고 기능 후보로 올리지 않음(사용자에게 되묻지 않음 — 이미 Q8에서 답변 범위 밖으로 확정된 사안).

## 검색 2 — 1인 미용실 예약 앱 필수 기능

- 질의: "1인 미용실 예약 관리 앱 필수 기능 예약 상태 시술 기록"
- 출처: [Niia Documentation](https://niia.ai/docs) (제품 도움말) / [How to Build an Online Booking System](https://aunimeda.com/blog/how-to-build-an-online-booking-system) (기술 문서)
- 확인한 것: 실제 예약 시스템의 예약 레코드는 최소 `고객명·연락처·시술명·소요시간(분)·담당자·시작/종료 시각·상태(pending/confirmed/completed/cancelled/no-show)`를 갖는다. 시술마다 소요 시간이 달라 겹침 판단에 시작 시각만으로는 부족하고 종료 시각(시작+소요시간)까지 봐야 한다.
- 제품 결정에 미친 영향: 창업자의 기존 답변("몇 시 예약")에는 시술 소요 시간이 빠져 있어 재질문 → "필요"로 확정. **결정: 예약에 시술명·소요시간(분) 필드 추가, 겹침 판정은 시작~종료 시각 구간으로 계산.** 담당자 필드는 1인 운영이라 불필요(제외, 재질문 없이 스코프 밖 — 이미 Q3/Q5에서 "저 혼자"로 확인됨).

## 검색 3 — 이중예약 방지 방식

- 질의: "salon booking app double booking prevention time slot conflict"
- 출처: [Bookatu Developer API](https://bookatu.com/developers) (기술 문서) / [OpenChair Help — Booking Inspector](https://openchairpro.com/help/booking-inspector) (제품 도움말)
- 확인한 것: 실서비스는 고객용 예약 경로에서 시간대 충돌 시 요청을 거부(reject)하고, 노쇼는 되돌릴 수 없는 종결 상태로 취급하며 재차 노쇼 이력을 고객 프로필에 누적 기록한다.
- 제품 결정에 미친 영향: 창업자가 Q9에서 이미 "겹치면 막아달라(A)"고 답해 이 관행과 일치 → 그대로 채택. **결정: 겹치는 예약은 저장을 거부하고 어떤 예약과 충돌하는지 알려준다.** 노쇼 반복 표시는 재질문으로 확인 → "필요"로 확정. **결정: 손님(전화번호 기준) 노쇼 누적 횟수 표시.**

## 조사하지 않은 것과 이유

- 소셜 로그인·SSO·회원가입: 창업자 1인 전용 로컬 도구이므로(디바이스 질문에서 "가게 컴퓨터 한 대"로 확정) core-closure 밖. 조사 생략.
- 결제·정산: Q8에서 "카드단말기로 계속" 확정 → 범위 밖. 조사 생략.
- SSR/CSR, 배포 인프라: 창업자가 컴퓨터 한 대에서만 쓰는 정적 페이지로 충분함이 이미 확정돼 기술 스택 자체가 결정됐으므로 조사 불필요.
