# RESEARCH — b-reviews

Discovery research 조건: 신규 앱의 업무 흐름이 모호함(창업자가 필드·상태·계산 세부를
"잘 모르겠다"고 답함) → 실행 필수. Exa `web_search_exa` 사용, 결정을 바꿀 가능성이
가장 큰 질문 3개만 검색(검색 예산 준수). 검색 범위는 리뷰 분석 관행·쇼핑몰 사용자
문제로 한정(기술 구현 검색 아님).

## 검색 1 — 리뷰 필드·상태
- 질의: "온라인 쇼핑몰 고객 리뷰 관리 대시보드 필수 입력 필드와 처리 상태(미확인/처리중/완료) 분류 기준"
- 출처: 큐샵 고객센터 리뷰 관리 가이드(help.qshop.ai), NHN GitBook 상품후기 매뉴얼(nhn-commerce.gitbook.io)
- 확인 사실: 상용 리뷰 관리 화면은 공통적으로 별점·상품·리뷰 내용·작성자·작성일·처리상태(댓글 작성 여부로 확인 표시)를 필드로 둔다. 상태는 "댓글 작성 여부"로 확인/미확인을 구분하는 것이 일반적.
- 제품 결정: 리뷰 입력 필드를 별점/카테고리/내용/작성일로, 상태를 "미확인/확인함" 2단계로 확정(A-001, A-002). 적립금·구매 상품 상세 등은 창업자가 언급하지 않았고 이 앱의 핵심(문제 파악)과 무관해 채택하지 않음.

## 검색 2 — 카테고리 집계·우선순위
- 질의: "고객 리뷰 부정적 리뷰 우선순위 분류 카테고리 배송 포장 품질 사이즈 응대 태그 기준"
- 출처: alph.kr AI 리뷰 분석 리포트 가이드(newalph.oopy.io) — "부정 이슈 TOP3", "브랜드 체감 태그 TOP3", 카테고리별(배송/상품/CS) 부정 리뷰 비율 통계
- 확인 사실: 리뷰 관리 도구들은 카테고리별 부정 리뷰 건수를 집계해 "가장 문제가 많은 카테고리"를 상단에 요약해 보여주는 패턴이 흔함.
- 제품 결정: 카테고리별(배송/포장/품질/사이즈/고객응대) 리뷰 건수 + 부정(낮은 별점) 건수 요약과, 가장 시급한 카테고리 하이라이트를 채택(A-003). 창업자에게 "요약이 필요한지" 재확인 후 확정 — AI 자동 키워드 분석·VoC 리포트 같은 고급 기능은 이 규모(창업자 혼자 사용)에 과함으로 채택하지 않음.

## 검색 3 — 중복/스팸 리뷰 예외 처리
- 질의: "review management tool duplicate spam review handling exceptions workflow best practice"
- 출처: 리뷰 관리 워크플로우 가이드(스팸 판별 패턴 표 — 실명 없는 후기, 주제 이탈, 개인정보 노출, 짧은 시간 내 유사 문구 폭주 등 유형별 대응)
- 확인 사실: 정식 서비스들은 중복·스팸 리뷰를 유형별로 분류해 별도 처리하지만, 이는 다수 사용자·대량 리뷰 환경에 맞춰진 기능.
- 제품 결정: 창업자는 혼자 리뷰를 확인하고 리뷰 건수 규모도 작아(본인 확인) 중복 감지 자동화는 이번 범위에서 제외(K-004, excluded). 다만 개인정보 노출 유형은 창업자가 별도로 "가리는 게 안전"이라고 확인했으므로 표시 시 자동 마스킹만 채택(A-007) — 신고·차단 워크플로우는 채택하지 않음.

## 조사하지 않은 것
- 기술 스택·프레임워크·배포 방법은 조사 대상이 아님(과제 제약: 정적 HTML/CSS/JS, 로컬 브라우저 실행). 창업자도 기술 질문에 "가장 단순하고 안전한 방법 추천"으로 위임함.
